# Story 10.2: Import Excel delle partite di un Campionato

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Allenatore del Gruppo iscritto a un Campionato (o Admin/Dirigente),
I want caricare un file Excel con tutte le gare della propria squadra in quel Campionato,
so that non devo inserire manualmente ogni partita una per una.

**Note aggiuntive:** seconda storia dell'Epic 10, dipende dalla Story 10.1 (`Campionato`/`GruppoCampionato` già esistenti, un Gruppo deve essere già collegato a un Campionato prima di poter importare le sue gare). Introduce la terza e ultima nuova entità dell'epic (`Partita`) e una **nuova dipendenza npm** (`xlsx`, decisione presa con l'utente in fase di creazione storia — vedi Dev Notes).

## Acceptance Criteria

1. **Given** un Allenatore (o Admin/Dirigente) su un Gruppo già collegato a un Campionato **When** carica un file Excel con le colonne attese (`Campionato, Gara N, Giornata, Data, Ora, SquadraCasa, SquadraOspite, Risultato, Parziali, StatoDescrizione, Impianto, IndirizzoImpianto`) **Then** ogni riga valida viene importata come Partita collegata a quel Campionato e a quel Gruppo
2. **Given** un file con una riga il cui `Gara N` corrisponde a una Partita già importata in precedenza per lo stesso Gruppo **When** il file viene ricaricato (es. per aggiornare i risultati di giornate nel frattempo disputate) **Then** la Partita esistente viene aggiornata sul posto (`upsert` su `(gruppoId, garaNumero)`), non duplicata
3. **Given** un file le cui intestazioni non contengono le colonne essenziali attese (`Gara N`, `Data`, `Ora`, `SquadraCasa`, `SquadraOspite`) **When** caricato **Then** l'intero import viene rifiutato con un messaggio di errore chiaro, nessuna Partita parzialmente importata
4. **Given** un file con intestazioni valide ma una singola riga con un valore essenziale mancante/non parsabile (es. `Data` non in formato `gg/mm/aaaa`) **When** importato **Then** quella riga viene scartata con un motivo esplicito, il resto del file viene comunque importato (stesso principio "scarta la riga, non l'intero file" già stabilito per l'import Atlete, Story 1.3)
5. **Given** un import (parzialmente o interamente) riuscito **When** completato **Then** viene mostrato un riepilogo (Partite create, aggiornate, righe scartate con motivo) — stesso pattern già usato per l'import Atlete
6. **Given** un Gruppo non ancora collegato al Campionato indicato (nessuna riga `GruppoCampionato` per quella coppia) **When** si tenta un import **Then** l'operazione viene rifiutata
7. **And** nessuna regressione sul resto del comportamento esistente (Story 10.1, import Atlete) — suite Vitest esistente invariata

### Review Findings

- [x] [Review][Decision] Chiave univoca di `Partita` non include `campionatoId` — un Gruppo collegato a più Campionati contemporaneamente (esplicitamente ammesso, Story 10.1 AC #5) può ricevere due export federali con lo stesso `Gara N` (la numerazione federale è tipicamente per girone/campionato, non globale). `@@unique([gruppoId, garaNumero])` in `prisma/schema.prisma`/`prisma/migrations/20260728020000_add_partita/migration.sql` e il `where: { gruppoId_garaNumero: ... } }` in `importa-gare-actions.ts:76` non includono `campionatoId`: importare le gare del Campionato B dopo quelle del Campionato A, con un `Gara N` che coincide per puro caso, troverebbe la Partita del Campionato A e la sovrascriverebbe silenziosamente con squadre/data/risultato del Campionato B (`update({ data: { ...riga, campionatoId } })`, riga 81). L'AC #2 della storia specifica letteralmente la chiave come `(gruppoId, garaNumero)` — cambiarla a `(gruppoId, campionatoId, garaNumero)` risolverebbe il problema ma devia dal testo dell'AC. Rilevato in modo indipendente sia da Blind Hunter sia da Edge Case Hunter. **Deciso con l'utente: allargare la chiave** — `@@unique([gruppoId, campionatoId, garaNumero])`, migrazione aggiornata di conseguenza (non ancora applicata dal vivo, sicuro modificarla in-place), `importa-gare-actions.ts` aggiornata a `gruppoId_campionatoId_garaNumero`, Prisma Client rigenerato, test aggiornati.

## Dev Notes

- **Perché una nuova dipendenza (`xlsx`) invece di riusare `exceljs`**: il file di riferimento reale fornito dall'utente (`_bmad/resources/Gare.xls`) è nel vecchio formato binario Excel (BIFF/OLE2, non OOXML) — verificato leggendo i byte del file (magic number `D0 CF 11 E0`). `exceljs` (`workbook.xlsx.load`) legge **solo** `.xlsx`. L'utente ha confermato esplicitamente che il file arriva **sempre** così dalla federazione/lega, senza possibilità di conversione manuale a `.xlsx` prima del caricamento (a differenza del vincolo già accettato per l'import Atlete, Story 1.3, che richiede `.xlsx`). `xlsx` (pacchetto npm, SheetJS community edition, versione `0.18.5` verificata su npm in fase di creazione storia) legge sia `.xls` sia `.xlsx` senza distinzione a priori — **decisione approvata esplicitamente dall'utente**, prima nuova dipendenza runtime introdotta in questo epic.
- **`exceljs` resta invariato**: nessun refactor di `import-atlete/parser.ts` per usare `xlsx` al posto di `exceljs` — quel modulo continua a funzionare com'è (accetta solo `.xlsx`, il che va bene per l'export federale Atlete). Le due librerie coesistono, ciascuna nel proprio ambito (AD-2).
- **Le intestazioni sono sulla prima riga** in questo file (a differenza dell'export federale Atlete, dove sono alla riga 5) — confermato leggendo il file reale con `xlrd` in fase di analisi. `XLSX.utils.sheet_to_json(sheet)` usa di default la prima riga come chiavi, il che si allinea perfettamente: non serve costruire manualmente una mappa colonna→indice come in `analizzaExportFederale`.
- **Colonne reali confermate dal file** (`_bmad/resources/Gare.xls`, 20 righe, campionato "Serie D femminile - Girone C", stagione 2025/2026): `Campionato, Gara N, Giornata, Data, Ora, SquadraCasa, SquadraOspite, Risultato, Parziali, StatoDescrizione, Impianto, IndirizzoImpianto`. `Impianto`/`IndirizzoImpianto` sono presenti su **ogni** riga, incluse le partite in casa (l'export non distingue "nostro impianto" da "impianto avversario") — nessuna Palestra dedicata da censire per gli avversari, il campo `indirizzoImpianto` è testo libero pronto per il meccanismo di navigazione Maps già esistente (`lib/link-naviga-palestra.ts`, Story 9.6 — riusato invariato, non in questa storia ma nella 10.3/10.5 dove le Partite vengono effettivamente mostrate).
- **`Gara N`/`Giornata` arrivano come `number` da `xlsx`** quando la cella contiene solo cifre (a differenza di `exceljs`, dove la cella Excel poteva già essere testo) — coercizione esplicita a stringa richiesta (`String(valore)`), altrimenti `Partita.garaNumero`/`giornata` (colonne `TEXT`) riceverebbero un tipo non atteso da Prisma.
- **`risolviAutorizzazioneGruppo` va estratta, non duplicata**: Story 10.1 l'ha introdotta come funzione privata in `app/(partite-campionati)/campionati/actions.ts` (righe ~27-93 dopo i fix di code review) — questa storia la sposta in `app/(partite-campionati)/autorizzazione.ts`, esportata, riusata identica da entrambi i file. Il refactor di `campionati/actions.ts` deve **preservare esattamente lo stesso comportamento** — i test esistenti in `campionati/actions.test.ts` non vanno modificati, solo continuare a passare (stesso principio già applicato all'estrazione di `validaNuovaPassword`, Story 9.11).
- **Nessun controllo di stagione aggiuntivo su `campionatoId` in questa storia**: la Story 10.1 (code review) ha già garantito che una riga `GruppoCampionato` esiste solo se Gruppo e Campionato condividono la stessa stagione (controllo introdotto in `collegaCampionatoEsistente`) — verificare solo l'esistenza della riga `GruppoCampionato` per la coppia `(gruppoId, campionatoId)` è quindi sufficiente, non serve ripetere il controllo di stagione da zero.
- **File NON da toccare**: `app/(onboarding-import)/import-atlete/actions.ts` (invariato, non tocca `Partita`), `lib/link-naviga-palestra.ts` (riusato in storie successive, non in questa), `lib/anno-agonistico/*` (nessuna nuova logica di stagione necessaria oltre a quanto già stabilito).
