# Story 14.2: Service Worker (funzionamento minimo offline e aggiornamento)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Utente che ha installato l'app,
I want che l'app resti minimamente utilizzabile e si aggiorni in modo prevedibile anche con connessione instabile,
so that non veda una schermata bianca/errore di rete generico ogni volta che la connessione cade per un istante.

## Acceptance Criteria

1. **Given** un utente con l'app installata perde la connessione **When** prova a navigare **Then** vede una pagina di fallback offline esplicita ("Connessione assente, riprova") invece dell'errore generico del browser
2. **Given** una nuova versione del Service Worker viene deployata **When** l'utente riapre l'app **Then** la nuova versione viene attivata automaticamente (`skipWaiting`/`clients.claim`), senza richiedere una disinstallazione/reinstallazione manuale
3. **And** nessun dato viene mai mostrato "stantio": il Service Worker non mette in cache HTML o risposte di chiamate dati/Server Action, solo asset statici immutabili
4. **And** nessuna regressione sulle Server Action esistenti — le mutazioni continuano a richiedere connessione attiva, con un messaggio di errore chiaro (non un crash) in sua assenza

## Dev Notes

### Perché nessuna libreria (Serwist/Workbox)

La guida ufficiale Next.js per PWA (`node_modules/next/dist/docs/01-app/02-guides/progressive-web-apps.md`, consultata come richiesto da `AGENTS.md`) raccomanda **Serwist** per il supporto offline, ma nota esplicitamente: *"this plugin currently requires webpack configuration"*. Questo progetto builda con **Turbopack** (`next build`/`next dev`, nessun flag `--webpack`) — introdurre Serwist richiederebbe forzare Webpack o una configurazione Turbopack non documentata dal progetto stesso, oltre a una nuova dipendenza npm mai approvata. Coerente con la decisione già presa in Story 14.1 (icone placeholder invece di una libreria di image-processing): **Service Worker scritto a mano**, ambito volutamente minimo come già delimitato in `epics.md` (cache-first solo per asset statici con hash, network-only per tutto il resto) — non serve l'orchestrazione di una libreria per tre casi di `fetch` così semplici.

### Scoperta tecnica: `headers()` e asset statici su Cloudflare

Ricerca web dedicata (necessaria: non è coperta da `node_modules/next/dist/docs/`, che documenta Next.js in generale, non lo specifico adapter di deploy di questo progetto) su `@opennextjs/cloudflare` + Cloudflare Workers Static Assets: **`next.config.ts` → `headers()` non si applica ai file serviti da `public/`** su questo tipo di deploy — il Worker Next.js non è nel percorso di richiesta per gli asset statici, serviti direttamente dal binding `ASSETS` (`wrangler.jsonc`). L'unico modo per impostare `Cache-Control` su `/sw.js` è un file `public/_headers` (convenzione Cloudflare nativa, sintassi `[url-pattern]` + righe indentate `Header: valore`, max 100 regole/file, parsato da Wrangler in fase di deploy — non da Next.js). Questo è un gotcha specifico di questa combinazione Next.js+Cloudflare, non un fatto generico su Next.js: se una futura ricerca riportasse la guida generica Next.js (`next.config.js` → `headers()` con `source: '/sw.js'`), **non è applicabile a questo progetto** per il motivo sopra.

### Versionamento cache

`CACHE_NAME` in `public/sw.js` non viene mai ribattezzato automaticamente da Next.js (a differenza di `_next/static/*`, che ha hash nel nome ad ogni build) — è un file statico copiato in `public/` senza alcuna trasformazione. Se una futura story cambia la logica di `install`/`fetch` di questo file senza incrementare manualmente la stringa di versione in `CACHE_NAME`, l'evento `activate` (Task 2) non troverà cache "vecchie" da eliminare (stesso nome = stessa cache, sovrascritta in-place) — non è un bug immediato, ma un lettore futuro di questo file deve sapere che il numero in `CACHE_NAME` è manuale e va incrementato ad ogni modifica sostanziale della strategia di cache, non lasciato invariato per abitudine.

### Cosa NON fare (ambito esplicitamente limitato da epics.md)

- **Nessuna cache di navigazioni HTML** oltre al singolo fallback `offline.html` precacheato — anche una pagina vista di recente non va servita dalla cache se la rete è disponibile (AC #3, motivato in epics.md: "il sito è quasi interamente dinamico... un Service Worker che mettesse in cache pagine/dati rischierebbe di mostrare informazioni stantie (presenze, certificati)").
- **Nessuna cache di chiamate dati/Server Action**, nemmeno per un TTL breve — stesso motivo.
- **Nessun banner "app aggiornata, ricarica"** o UI di gestione dell'aggiornamento — fuori scope, AC #2 richiede solo l'attivazione automatica silenziosa (`skipWaiting`/`clients.claim`), non un'interazione con l'utente.
- **Nessuna Web Push Notification** — la guida Next.js PWA le tratta insieme al Service Worker, ma non è nello scope di questo epic/story (`epics.md` non le menziona).

### Previous Story Intelligence (Story 14.1)

- Il `matcher` di `middleware.ts` **non ammette gruppi di cattura catturanti** — solo `(?:...)`. Scoperto in Story 14.1 durante l'applicazione di un fix di code review: `npm run build` fallisce con `Invalid route source`/`Capturing groups are not allowed at <N>` se violato. Verificare sempre con `npm run build` dopo ogni modifica al `matcher`, non fidarsi di `tsc`/`eslint` (che non validano la sintassi del pattern).
- `.` va sempre escappato (`\\.`) nel `matcher` quando si intende il punto letterale di un'estensione file (`favicon\\.ico`, `manifest\\.webmanifest`) — un `.` non escappato in regex corrisponde a "qualunque carattere", errore già commesso e poi corretto in Story 14.1.
- Zero nuove dipendenze npm senza approvazione esplicita dell'utente — regola del workflow `dev-story`, già rispettata in Story 14.1 (icone scritte a mano invece di `sharp`/`jimp`) e vincolante anche qui (niente Serwist, vedi Dev Notes sopra).
- La verifica dal vivo di comportamenti browser/dispositivo reali non è possibile in questo ambiente sandbox — pattern consolidato (Story 12.4, 13.1, 14.1): documentare esplicitamente cosa resta da verificare dopo il deploy invece di assumerne il funzionamento.
